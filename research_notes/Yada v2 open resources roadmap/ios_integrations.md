# iOS platform integrations for Yada (calm, offline-first, no-account Bible reading app)

Scope note: this brief was asked to be current as of October 2026 and to cover "iOS 26". The Expo SDK 58 beta changelog already announces "iOS 27 support" and the v58 expo-app-intents docs cite iOS 27 and Xcode 27 APIs ([Expo SDK 58 beta](https://expo.dev/changelog/sdk-58-beta); [expo-app-intents v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md)). So iOS 27 is probably shipping now, and anything below that says "iOS 26" is a floor, not the newest release. Yada is on Expo SDK 57 / RN 0.86. SDK 57 shipped June 30, 2026 as a small, non-breaking RN 0.85 to 0.86 release ([releases.sh summary of Expo SDK 57](https://releases.sh/release/rel_aH7NaXbDXMlY2_I-Ak0D0-expo-sdk-57-upgrades-to-react-native-0-86-with-no-breaking-changes); [Expo SDK 57 changelog](https://expo.dev/changelog/sdk-57)).

Tool budget: about 20 searches and fetches. Competitor App Store pages, fetched through a summariser, did not reliably show the "Supports" section (Widgets, Apple Watch, CarPlay, Siri), so the competitor data has holes. They are listed under Gaps rather than guessed.

## Which 3–4 integrations give the most value for least effort?

### Takeaway
The best value for effort is: (1) Home Screen and Lock Screen widgets through Expo's own `expo-widgets`, offering "Continue reading" and a calm passage of the day; (2) Now Playing / lock-screen media controls for the read-along audio, which also brings a free Live Activity-style presence where the system allows it, plus CarPlay *Live Activity* display on iOS 26 without a CarPlay entitlement; (3) App Intents for "Open [book chapter]" and "Continue reading", with Spotlight indexing through `expo-app-intents`, which is SDK 58 alpha and so arrives with the next SDK bump; (4) Assistive Access full-screen opt-in, which is one Info.plist key. Apple Watch, a full CarPlay app, and SharePlay are high effort for little value at Yada's stage.

### Cited Findings

**Widgets (WidgetKit) through expo-widgets, the official Expo library**
- `expo-widgets` builds iOS Home Screen widgets, Lock Screen widgets and Live Activities from React components using `@expo/ui` SwiftUI components. A config plugin generates the Widget Extension target, the App Group and the files at prebuild, so no hand-written Swift is needed ([Expo blog, Mar 4 2026](https://expo.dev/blog/home-screen-widgets-and-live-activities-in-expo)).
- Families supported in the SDK 57 docs: systemSmall, systemMedium, systemLarge, systemExtraLarge (iPad), and the Lock Screen accessoryCircular, accessoryRectangular and accessoryInline ([expo-widgets v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).
- Data API: `updateSnapshot(props)`, `updateTimeline(entries)` with dated entries, `getTimeline()` and `reload()`. App and widget share data through an App Group (default `group.<bundleId>`) and a shared `widgetsDirectory` for images ([expo-widgets v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)). A dated timeline suits a passage of the day that is precomputed offline for the next N days.
- Interactive Buttons (iOS 17+) can return new props without launching the app, and configurable widgets with user-editable parameters (iOS 17+) are supported ([expo-widgets v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).
- Constraint: widget components run in an isolated JS runtime and may use only `@expo/ui/swift-ui` components, with no hooks, state, context, async work, imports or module-scope references ([expo-widgets v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).
- Maturity is unclear. The changelog shows 55.0.0 stable on 2026-02-25 after alphas. 56.x brought breaking changes (minimum iOS 16.4, `containerBackground` moved to a modifier), configurable widgets (56.0.8), a shared image directory (56.0.17) and opt-in Android. 57.0.0 (2026-06-25) had "no user-facing changes" ([expo-widgets CHANGELOG](https://unpkg.com/expo-widgets@57.0.0/CHANGELOG.md)). The March 2026 blog and the latest docs still call it alpha and "subject to breaking changes" ([Expo blog](https://expo.dev/blog/home-screen-widgets-and-live-activities-in-expo); [latest docs search snippet](https://docs.expo.dev/versions/latest/sdk/widgets/)). One search summary cited an Expo post of June 18, 2026 saying it was stable from SDK 56 ([search result pointing to expo.dev blog](https://expo.dev/blog/ios-widgets-and-live-activities-in-expo)). That claim was not verified and conflicts with the docs.
- The March 2026 blog said ExpoUI did not yet support images, and that timeline readback and refresh policies were still planned ([Expo blog](https://expo.dev/blog/home-screen-widgets-and-live-activities-in-expo)). The SDK 57 docs now list `getTimeline()` and a shared image directory, so these appear to be resolved ([v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).
- Competitor use: YouVersion added "Verse of the Day widgets" for the home screen (seen in the Android 8.18.2 release notes) ([APKMirror YouVersion 8.18.2](https://apkmirror.com/apk/life-church/bible/bible-8-18-2-release)). An ESV Bible reviewer (Feb 2024) praised "widgets... to see the verse of the day" ([ESV Bible App Store](https://apps.apple.com/us/app/esv-bible/id361797273)). A whole category of single-purpose Lock Screen verse widget apps exists, often paired with streak trackers, for example "From Bible: Bible Widgets" with a "daily reading streak tracker" and "Bible Hour" with a "daily meditation streak" and an Apple Watch app ([From Bible listing](https://mwm.ai/apps/app/6759759625); [Bible Hour App Store](https://apps.apple.com/us/app/id1553619820)).
- iOS 26 shows `systemSmall` widgets in CarPlay. A developer forum post notes there is no documented way to tell whether a widget is rendering on CarPlay or on iPhone ([Apple Developer Forums, Widgets & Live Activities](https://developer.apple.com/forums/forums/topics/app-and-system-services/app-and-system-services-widgets-and-live-activities)).
- Review: widgets "should relate to your app's content and functionality" (2.5.16). Extensions may not include marketing, ads or IAP (4.4), and display ads may not appear in widgets (2.5.18) ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).

**Live Activities / Dynamic Island for the read-along audio**
- `expo-widgets` provides `createLiveActivity`, `start`, `update` and `end` (with dismissal policy and `contentDate`), `getInstances` for recovery after relaunch, and push tokens. Push is optional (`enablePushNotifications` defaults to false), so a local-only Live Activity needs no server ([expo-widgets v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)). SDK 58 beta adds a `staleDate` option ([Expo SDK 58 beta](https://expo.dev/changelog/sdk-58-beta)).
- Apple HIG says to use them for tasks with a defined start and end, up to eight hours. End them as soon as the task ends. Update only when content changes. Make them easy to turn off. Never use them for ads or promotions. Show no sensitive information. Media playback is named as a fitting interactive use, and a single interactive element is preferred ([HIG: Live Activities](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/live-activities.json)).
- Where they appear: Lock Screen, Home Screen, Dynamic Island and StandBy (StandBy shows the minimal presentation and expands 2x on tap). They also appear in the paired Mac menu bar, in the Apple Watch Smart Stack (leading and trailing compact elements by default, with no watch app needed), and in the CarPlay Dashboard with interactive elements disabled (`ActivityFamily.small` gives a custom layout) ([HIG: Live Activities](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/live-activities.json)). Since watchOS 11, the Smart Stack shows iPhone Live Activities with "no changes to your code at all" ([WWDC24 10068 notes](https://wwdcnotes.com/documentation/wwdc24-10068-bring-your-live-activity-to-apple-watch/)). In iOS 26, Live Activities on iPhone display in CarPlay ([search summary of 9to5mac / Apple sources](https://9to5mac.com/?p=1014979)).
- Review 4.5.3 explicitly forbids using Live Activities to spam or send unsolicited messages ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).

**App Intents / Siri / Shortcuts / Spotlight**
- `expo-app-intents` (alpha, "will frequently experience breaking changes") is documented only for SDK 58. The v57 docs URL returns 404, so it is **not available on Yada's current SDK 57** ([v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md); [v57 URL 404](https://docs.expo.dev/versions/v57.0.0/sdk/app-intents.md)). It needs iOS 16.4+ and doesn't run in Expo Go.
- Intent types must be declared in Swift (Swift inline modules, so Apple's build-time metadata extraction finds them). JS gets an at-least-once invocation queue (capped at 100, oldest dropped, handlers must be idempotent by invocation `id`) ([v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md)).
- AppShortcutsProvider: phrases are compiled, not added from JS. Each must include `\(.applicationName)`, can interpolate at most one non-array parameter, and an app can have up to 10. AppEntity/EntityQuery read a catalog JS publishes through `setEntityCatalogAsync()` into UserDefaults, which should stay compact. Spotlight: `registerIndexed`, `hideInSpotlight` and `reindexEntitiesAsync()`. Intent donation: `donateIntentAsync()` ([v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md)).
- Setup: add the plugin, set `experiments.inlineModules.watchedDirectories`, then run `npx expo-app-intents init [--examples --visual-intelligence --donations]` ([v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md)).
- Alternatives: `@avasapp/react-native-app-intents` was created in May 2026 and has very few stars, so its maturity is unknown ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Favas-app%2Freact-native-app-intents)). `react-native-siri-shortcut` with `@config-plugins/react-native-siri-shortcut` uses the older SiriKit-style flow ([npm](https://npmjs.org/package/@config-plugins/react-native-siri-shortcut)). `expo-apple-targets` lists `app-intent`, `intent` and `intent-ui` target types ([expo-apple-targets README](https://github.com/EvanBacon/expo-apple-targets)).
- Competitor use: YouVersion 11.32.0 (Sep 16) added "Ask Siri to play Bible audio chapters" ([YouVersion App Store](https://apps.apple.com/us/app/bible/id282935706)).
- Review 2.5.11: only register intents the app can handle, resolve requests "as directly as possible", and put no ads or marketing in Siri or Shortcuts flows ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- A secondhand claim says WWDC 2026 deprecated SiriKit in favour of App Intents ([vp0.com blog](https://vp0.com/blogs/siri-shortcuts-integration-react-native-ai)). Not verified against Apple sources.

**Assistive Access**
- iOS 26 added the Info.plist key `UISupportsFullScreenInAssistiveAccess`. With it set, the app keeps its normal UI but fills the full screen in Assistive Access and appears under "Optimized Apps" in Accessibility settings. Runtime detection is available through `isAssistiveAccessEnabled` / SwiftUI `accessibilityAssistiveAccessEnabled`. The other option is a dedicated Assistive Access scene with system-styled controls ([WWDC25 session 238](https://developer.apple.com/videos/play/wwdc2025/238/); [Apple: Optimizing your app for Assistive Access](https://developer.apple.com/tutorials/data/documentation/accessibility/optimizing-your-app-for-assistive-access.md)).
- Apple's guidance asks that a full-screen app's UI be adaptive and not depend on fixed screen sizes ([Apple docs](https://developer.apple.com/tutorials/data/documentation/accessibility/optimizing-your-app-for-assistive-access.md)).

**CarPlay (full app)**
- A CarPlay app needs a category entitlement requested from Apple (Audio, among others) and agreement to the CarPlay Entitlement Addendum. Apple reviews each request against fixed criteria ([Apple: Requesting CarPlay entitlements](https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements.md)). Audio apps must be "designed primarily to provide audio playback services" ([CarPlay App Programming Guide](https://Developer.apple.com/carplay/documentation/CarPlay-App-Programming-Guide.pdf)). App Review calls the CarPlay Audio entitlement a limited-use entitlement ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- The template is tied to the category. A forum case lost access to `CPNowPlayingTemplate` once the app was classified as a navigation app ([Apple forum 804008](https://developer.apple.com/forums/thread/804008)).
- Competitor use: Dwell lists Apple CarPlay and Android Auto for hands-free listening ([Dwell help](https://help.dwellapp.io/article/100-what-is-the-difference-between-dwell-and-other-bible-apps); [Dwell help 2](https://intercom.help/dwell-ea861300b36d/en/articles/15213896-what-makes-dwell-unique)). Dwell is a recorded audio Bible, which is exactly the use case the entitlement is meant for.

**Apple Watch**
- `expo-apple-targets` lists `watch` and `watch-widget` targets but warns that the list is "based on static analysis... may not work" ([README](https://github.com/EvanBacon/expo-apple-targets)).
- Competitor use: YouVersion shipped a Watch app in 2015 (Verse of the Day, bookmarks) ([Gospel Herald 2015](https://www.gospelherald.com/articles/55099/20150410/youversion-release-updated-version-bible-app-apple-watch.htm)). Its current App Store compatibility list shows iPhone, iPad, Vision and Apple TV, with no Watch listed ([YouVersion App Store](https://apps.apple.com/us/app/bible/id282935706)). Hallow lists iPhone, iPad and Mac only ([Hallow App Store](https://apps.apple.com/us/app/hallow-prayer-meditation/id1405323394)). An older AppleVis review lists Dwell's Watch support as "No" ([AppleVis](https://applevis.com/comment/90709)).

**Control Center controls (iOS 18+)**
- `expo-apple-targets` supports control widgets inside a widget target, with iOS 18 APIs in its example and a default deployment target of iOS 18.0 ([README](https://github.com/EvanBacon/expo-apple-targets)). The expo-widgets v57 docs do not mention Control Center controls ([v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).

**expo-apple-targets (community, Evan Bacon)**
- Supports about 50 target types (widget, app-intent, watch, share, action, clip and others). It requires CocoaPods 1.16.2+, Xcode 16+ and Expo SDK 53+. The repo has 425 commits, 1.4k stars, 48 open issues and 23 open PRs, with no tagged releases. The latest commit date was not visible ([README](https://github.com/EvanBacon/expo-apple-targets)). One write-up quotes it as "highly experimental and not part of any official Expo workflow" ([fusic tech blog](https://tech.fusic.co.jp/posts/expo-apple-widget/)). Widget UI is still written in SwiftUI ([Expo blog](https://expo.dev/blog/home-screen-widgets-and-live-activities-in-expo)).

### Inferences
- **Ranking (value ÷ effort):**
  1. **Widgets through expo-widgets, on SDK 57 now.** "Continue reading" (small/medium: book, chapter, passage title, tap opens it with a deep link) and a calm "Today's passage" (accessoryRectangular / medium) are the visible wins. A passage of the day can be a precomputed offline timeline from the bundled corpus, with no network and no background fetch. Widgets show up in StandBy and, as systemSmall, in CarPlay on iOS 26, so one target covers several surfaces. Effort: low to medium (config plugin plus an `@expo/ui` component). The alpha label means pinning versions and testing on each SDK bump.
  2. **App Intents and Spotlight, after moving to SDK 58.** "Open John 3" (one parameter: a passage entity) and "Continue reading" (no parameter) as App Shortcuts, plus indexing reviewed passages and the user's bookmarks as IndexedEntity. These also feed the Action button, Spotlight, Siri and Shortcuts, and are the foundation for Control Center controls and Focus filters. Effort: medium, because a small amount of Swift is unavoidable.
  3. **Live Activity for read-along audio.** Local-only, started when TTS playback starts and ended when it stops. It shows passage, verse and play/pause. It then appears for free on the Lock Screen, in the Dynamic Island, in StandBy, in the Watch Smart Stack and on the CarPlay Dashboard (iOS 26), which removes most of the reason to build a Watch app or a CarPlay app. Effort: low to medium with expo-widgets, which Yada would already be using.
  4. **Assistive Access full-screen key.** One Info.plist line through `app.json` `ios.infoPlist`. It fits Yada's accessibility-first rule exactly. Effort: trivial, plus a QA pass.
- **Per-integration fit summary (inferences, partly from prior platform knowledge not re-verified this session):**
  - *Now Playing / MPNowPlayingInfoCenter + MPRemoteCommandCenter:* this is the base layer for lock-screen controls, AirPods controls and CarPlay Now Playing. AVSpeechSynthesizer output is not a media item, so Yada's native audio module would have to publish now-playing info and handle remote commands itself. Unverified: whether Apple would accept a TTS-only app as "primarily audio" for the CarPlay Audio entitlement. Recorded audio apps like Dwell clearly qualify. Yada's synthesized read-along may not.
  - *Control Center control (iOS 18+):* a single "Continue reading" or "Play today's passage" button. Needs a ControlWidget (Swift) wired to an App Intent, either through expo-apple-targets or a hand-written Swift file. Value is low to medium, effort medium. Do it after App Intents exist.
  - *Focus filters (SetFocusFilterIntent):* could, for example, switch the app to a "quiet" mode or a chosen translation under a "Rest" or "Sabbath" Focus. This is an App Intent, so it comes after #2. Value is niche.
  - *Handoff (NSUserActivity):* iPhone and iPad continuity of the open passage. Small effort, but needs a native module or a Swift inline module. Could reuse the same activity type as Spotlight donations.
  - *SharePlay / GroupActivities:* group reading in sync over FaceTime. High effort (native GroupActivities plus a sync model), and it adds a social surface. No competitor evidence was found. Defer.
  - *iCloud sharing (CKShare):* would mean moving from key-value sync to CloudKit records. High effort. It conflicts with the minimalism of no accounts (although it uses Apple ID, not a Yada account).
  - *Apple Watch app:* high effort (a separate watchOS target, SwiftUI, an experimental target type), and the Smart Stack Live Activity covers the main need. The major competitors don't currently list Watch support.
  - *StandBy:* no separate work. It comes from widgets and Live Activities, so it is worth testing the widget's StandBy rendering in red night mode for evening reading.

## What does Expo 57 / RN 0.86 support natively vs needs a native target?

### Takeaway
On SDK 57 the only first-party path is `expo-widgets` (widgets plus Live Activities, generated target, alpha). Everything else needs either a Swift target or extension through `expo-apple-targets` (Watch, Control Center controls, share extensions), Swift inline modules through `expo-app-intents` (SDK 58+, alpha), or a custom Expo native module (Now Playing, Handoff, SharePlay, Focus filter handling, CarPlay scene). Info.plist-only features (Assistive Access) need nothing but app config.

### Cited Findings
- SDK 57: RN 0.85 to 0.86, React 19.2 unchanged, "no breaking changes", and prebuild now clears native dirs. expo@57.0.17 moved to RN 0.86.3 to fix a Hermes V1 memory regression ([releases.sh](https://releases.sh/release/rel_aH7NaXbDXMlY2_I-Ak0D0-expo-sdk-57-upgrades-to-react-native-0-86-with-no-breaking-changes); [Expo SDK 57 changelog](https://expo.dev/changelog/sdk-57)).
- `expo-widgets` v57: a first-party config plugin generates the extension (`<appId>.ExpoWidgetsTarget`) and App Group. It is not in Expo Go and needs dev builds. Live Activities must *not* get a `widgets[]` entry, or an invalid target is generated ([v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).
- `expo-app-intents`: v58 only (v57 docs 404). Intents are written in Swift, and JS handles catalog, queue and donations ([v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md); [v57 404](https://docs.expo.dev/versions/v57.0.0/sdk/app-intents.md)). The SDK 58 beta pairs with RN 0.88 RC and "new JavaScript APIs for Siri, Shortcuts, and Apple Intelligence" ([Expo SDK 58 beta](https://expo.dev/changelog/sdk-58-beta)).
- `expo-apple-targets`: puts a `/targets` directory into Xcode as virtual targets. It is not an official Expo workflow, Watch, control and intent targets are untested, and it defaults to iOS 18.0 ([README](https://github.com/EvanBacon/expo-apple-targets); [fusic](https://tech.fusic.co.jp/posts/expo-apple-widget/)).
- Assistive Access is an Info.plist key (`UISupportsFullScreenInAssistiveAccess`) ([Apple docs](https://developer.apple.com/tutorials/data/documentation/accessibility/optimizing-your-app-for-assistive-access.md)).
- CarPlay requires an Apple-granted entitlement plus App ID and provisioning changes ([Apple](https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements.md)).

### Inferences
- Map:
  - **Config only:** Assistive Access key; Spotlight via NSUserActivity is not config-only.
  - **First-party plugin, JS UI:** widgets (Home Screen, Lock Screen, StandBy, CarPlay small), Live Activities (Dynamic Island, Smart Stack, CarPlay Dashboard).
  - **First-party plugin + Swift (SDK 58):** App Intents, App Shortcuts, Spotlight IndexedEntity, intent donation, visual intelligence (`--visual-intelligence` scaffold).
  - **Community target + Swift:** Control Center controls, Watch app, Watch complications.
  - **Custom native module:** Now Playing / remote commands for AVSpeechSynthesizer read-along (Yada's existing native audio module is the natural home), Handoff, SharePlay, the CarPlay scene delegate.
- Because Yada's widget, App Intents and Live Activity work all share an App Group, set the App Group ID once (the expo-widgets default `group.<bundleId>`) and reuse it so both targets read the same "last position" record. iCloud KV sync already holds position. The app should copy it into the App Group on each change so the widget never needs network.
- A sensible sequence is: ship widgets and the Assistive Access key on SDK 57, then upgrade to SDK 58 for App Intents, Spotlight and the Live Activity `staleDate`.

### Gaps
- Not confirmed whether `expo-widgets` v57 can host a ControlWidget, or whether expo-apple-targets and expo-widgets can coexist in one project without target-name or App Group conflicts.
- Not checked: whether `expo-audio` (or any Expo module) publishes MPNowPlayingInfo for non-file audio such as TTS. Probably not, but unverified.

## Any that would undermine Yada's principles (notifications nagging, streaks)?

### Takeaway
None of the integrations needs nagging, streaks or an account. The risks are in *how* they are used: streak and counter widgets (common in the verse-widget category), push-driven Live Activities or reminders, and Apple Intelligence system features (Writing Tools, visual intelligence, on-screen entity association) that could pass licensed NIV/NKJV/NLT text to AI. That last one is the main conflict with Yada's rule 9 and has to be handled on purpose.

### Cited Findings
- The verse-widget app category commonly bundles streaks: "daily reading streak tracker" ([From Bible](https://mwm.ai/apps/app/6759759625)), "daily meditation streak... streaks can sync" ([Bible Hour](https://apps.apple.com/us/app/id1553619820)).
- Competitor privacy labels, for contrast with no-account Yada: YouVersion links Contact Info, User Content, Search History and User ID to the user and uses data for advertising/marketing and analytics ([YouVersion App Store](https://apps.apple.com/us/app/bible/id282935706)). Hallow lists "Data Used to Track You: Purchases, Identifiers" ([Hallow App Store](https://apps.apple.com/us/app/hallow-prayer-meditation/id1405323394)). ESV links purchase history, email, name and user ID ([ESV App Store](https://apps.apple.com/us/app/esv-bible/id361797273)).
- HIG: Live Activities must not carry ads or promotions, should alert only for essential updates, and should not duplicate push notifications ([HIG](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/live-activities.json)). App Review 4.5.4: push must not be required to use the app, and marketing push needs explicit opt-in. 4.5.3: no spam through Live Activities ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)).
- expo-widgets Live Activity push is opt-in (`enablePushNotifications: false` by default), so local-only operation is supported ([v57 docs](https://docs.expo.dev/versions/v57.0.0/sdk/widgets.md)).
- `expo-app-intents` exposes Apple Intelligence entry points: on-screen entity association (`appEntityIdentifier()`, `AppEntityView`, iOS 18.4+), schema intents (useful only for primary domains such as mail, photos and files), and a visual-intelligence scaffold ([v58 docs](https://docs.expo.dev/versions/v58.0.0/sdk/app-intents.md)).

### Inferences
- **Widgets:** fine if they show only the passage (title plus an opening line, or just a reference) and "continue". Never a day counter, "X days in a row", or a progress ring. A passage-of-the-day widget should not imply an obligation. Avoid "You haven't read today" states. The widget timeline is local, so it works offline and needs no notification permission.
- **Live Activities:** use them only while read-along audio is actually playing, end them on stop, and never start one remotely. That matches both HIG and "no guilt".
- **Notifications:** none of the top four integrations needs notification permission. Leave reminders out entirely or keep them strictly opt-in. App Intents and widgets give a pull-based "come back" path instead of push.
- **Licensed text and Apple Intelligence (rule 9).** From Yada's side, the risk points are:
  - (a) Publishing on-screen entity content or IndexedEntity descriptions for passages in a licensed translation. Fix: entity payloads should carry only references and Yada-owned text (BSB/WEB/KJV/LSV), never NIV/NKJV/NLT verse text.
  - (b) Spotlight indexing licensed verse text. Same fix: index the reference plus the public-domain/BSB text only.
  - (c) System Writing Tools and visual intelligence acting on selectable licensed text on screen. This is user-initiated and done by the OS, not a Yada "AI call". Yada's rule is stricter than API.Bible §9.2 ("no AI call... not prompts, grounding..."), so the conservative position is to disable Writing Tools on text views that render licensed translations, and to skip a visual-intelligence hook on licensed screens.

  Whether RN Text components expose Writing Tools and how to opt out (UIKit `writingToolsBehavior`) was **not verified in this session**. It needs a check, and it is a policy call for John, not a technical one.
- **Apple Intelligence on Yada-generated content:** Siri or Shortcuts surfacing the reviewed passage guide is fine under rule 9, since it is built only from Greek, Hebrew, BSB, WEB, KJV and LSV. But "Generated content is flagged / only John approves". Any intent that returns guide text should return only `approved` entries, never `flagged` ones.
- **SharePlay / iCloud sharing:** neither breaks a principle, but both add social features and complexity that cut against "calm". Defer.
